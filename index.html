8 · Introduction

Testing has two distinct goals

Software testing is an important process in the software development lifecycle. It checks the software from two directions.

Verification

“Are we building the product right?”

The software should conform to its specification: its functional and non-functional requirements.

vs
Validation

“Are we building the right product?”

The software should do what the customer really requires.

Barry Boehm summed these up in 1979. Verification: are we building the product right, meaning does it match the specification? Validation: are we building the right product, meaning does it do what the customer actually needs?

A system can pass verification and still fail validation if the specification itself was wrong.

8.1

Section 8.1

Development
testing

Development testing is the responsibility of the software development team. It happens while the system is being built, and its main job is to find bugs.

Later, a separate team tests the system before it is released to customers. In user testing, customers or system users provide test data and check that tests are successful.

Unit testingOne function, method or object class, tested in isolation.
Component testingSeveral units combined, tested through one interface.
System testingAll components integrated and tested as a whole.
  1. Stage 1 · nowDevelopment testingDevelopment team
  2. Stage 2Release testingSeparate testing team
  3. Stage 3User testingCustomers and users

A commercial system goes through three stages of testing: development testing by the team building it, release testing by a separate team, and user testing by customers.

Inside development testing there are three levels, from small to large: unit, component and system testing. Development testing is mainly defect testing: the aim is to find bugs.

8.1.1 · Development testing

Unit testing

Unit testing is the process of testing individual components in isolation.

A unit can be a single function or method, or a whole object class with several attributes and methods.

Goal: complete test coverage of a class
  • Test all operations associated with the object
  • Set and interrogate all object attributes
  • Exercise the object in all possible states
WeatherStation
identifier
  • reportWeather()
  • reportStatus()
  • powerSave(instruments)
  • remoteControl(commands)
  • reconfigure(commands)

State sequences to test
Shutdown→Running→Shutdown
Configuring→Running→Testing→Transmitting→Running
Running→Collecting→Running→Summarizing→Transmitting→Running

Units are the smallest testable parts: functions and methods, or object classes.

The example is a WeatherStation class from a remote weather system. Complete coverage means calling every operation, setting and reading the identifier attribute, and driving the object through its state model, for example Shutdown → Running → Shutdown, or Configuring → Running → Testing → Transmitting → Running.

8.1.2 · Development testing

Choosing unit test cases

Two types of unit test case

NORMALShow it works

Test cases that show the component behaves correctly under normal use, for example by demonstrating part of a use case.

login("dara", "c0rrect-pw") → "Welcome, Dara"

ABNORMALExpose the bugs

Test cases that expose defects. For example, invalid input should produce an error message and fail gracefully.

login("", "") → "Please enter your username"
Two strategies for choosing them

Partition testing

Identify groups of inputs that have common characteristics and should be processed in the same way. Choose tests from within each of these groups.

ages: [<0 invalid] [0–17 minor] [18–120 adult] [>120 invalid]

Guideline-based testing

Use testing guidelines based on the kinds of errors that programmers often make. Choose tests based on these guidelines.

empty list · one item · first/middle/last · overflow

Testing is expensive, so test cases must be chosen well. Every component needs both kinds: tests that show it works under normal use, and tests that probe for defects with abnormal inputs.

The two strategies are partition testing, which groups inputs into classes that behave the same way, and guideline-based testing, which uses experience of common programming mistakes. The next two slides show each one.

8.1.3 – 8.1.4 · Development testing

Component and system testing

8.1.3 · Component testing

Components are made of several interacting objects, used through a defined interface.

Component testing shows the interface behaves according to its specification, assuming the objects inside have already been unit-tested.

8.1.4 · System testing

Integrate components to create a version of the system, then test the integrated system.

It checks that components
  • are compatible
  • interact correctly
  • transfer the right data at the right time across their interfaces

It tests the interactions between components, including behaviour that only appears when the parts run together.

Real case: the Mars Climate Orbiter was lost because one module sent pound-force seconds and the other read newton seconds. Each part worked alone; the interface failed.

Component testing checks a group of objects through its interface, assuming each object already passed its unit tests. Common interface errors are misuse (wrong parameters), misunderstanding (wrong assumptions) and timing errors.

System testing puts all components together and tests how they interact. The Mars Climate Orbiter shows why: each module was correct on its own, but they disagreed about units.

8.2 · Test-driven development

Write the test first

Test-driven development (TDD) is an approach in which testing and code development are interleaved (Beck, 2002). The cycle: red, green, refactor, repeat.

1/5Identify a small increment of functionality, normally a few lines of code.

2/5Write a test for it and implement the test as an automated test.

3/5Run it with all the other tests. It fails, because the code doesn't exist yet.

4/5Implement the functionality and refactor, then run the tests again.

5/5All tests pass. The new code is now protected by its own test.

nextMove on to the next chunk of functionality and repeat the cycle.

cart.test.js
// Feature: orders over $100 get 10% offtest("10% off orders over $100", () => {  expect(total(120)).toBe(108);}); function total(amount) {  return amount > 100 ? amount * 0.9 : amount;}
$ npm test -- --watch

↻ code changed, re-running…
✓ 10% off orders over $100 (2 ms)
Tests: 1 passed
Next: free shipping over $200 →

TDD means testing and coding are interleaved. Identify a small piece of new functionality, write an automated test for it, and run it with all the other tests. It fails, so you implement the functionality and refactor, then run the tests again. When everything passes, move to the next piece.

The editor on the right plays a real cycle: the test for a 10% discount fails first because total() doesn't exist, then passes once it is written. The same discount comes back in the release testing example.

8.2 · Test-driven development

Four benefits of writing tests first

Code coverage

Every piece of code has at least one test, so high coverage means the code is thoroughly tested.

Regression testing

The test suite grows with the code. Re-running it checks that new changes or additions haven't broken anything.

let sum = 0;
for (const i of items)
sum += i.price * 0.9;
return round(sum);

Simplified debugging

When a test fails, the problem can usually be pinpointed to the code just written.

applies 10% off over $100
rejects negative totals
free shipping over $200
rounds to 2 decimals

System documentation

The tests describe what the code is supposed to do, and they never go out of date.

TDD works best for new code. It helps less with large legacy systems and is harder to apply to multithreaded code.

Code coverage: every code segment has at least one associated test. Regression testing: a suite develops incrementally and can be run after every change, which is cheap because it's automated. Simplified debugging: a failing test points at the code you just wrote. Documentation: tests read as a description of what the code should do.

Studies of TDD are mixed on productivity, but most report better code quality and better understanding of the code.

Release
testing

Release testing is the final testing stage before software is released to users.

◎

Goal: make sure the software is ready for deployment and meets all user requirements and performance standards.

≡

Process: typically a suite of test cases that cover requirements, scenarios and performance.

How it differs from system testing
Release testingSystem testing
WhoA separate team, not the developersThe development team
AimValidation: is it good enough to release?Defect testing: find bugs
StyleBlack-box, from the specificationCan use knowledge of the code
  1. Stage 1 · doneDevelopment testingDevelopment team
  2. Stage 2 · nowRelease testingSeparate testing team
  3. Stage 3User testingCustomers and users

Release testing checks a particular release of a system that is intended for use outside the development team.

There are two differences from system testing: it should be done by a separate team that has not been involved in development, and its aim is validation, showing the system is good enough to use, rather than finding bugs. It is usually black-box testing based on the specification.

8.3.1 – 8.3.2 · Release testing

Requirements and scenario testing

8.3.1 · Requirements-based testing

Verifies that the software meets each specified requirement. Test cases are designed to cover individual requirements, so each one is checked as correctly implemented.

Example · banking app

“Users must be able to transfer money in less than 5 seconds.”

TC-1Transfer $50 between own accounts1.8 s ✓
TC-2Transfer to another bank3.1 s ✓
TC-3Transfer at peak time4.6 s ✓
8.3.2 · Scenario testing

Validates complex user workflows end to end, so the software behaves as expected in real-world use. It finds problems that individual functional tests miss.

The tester follows the exact steps in the app, checking each action works smoothly as part of one workflow.

Example · social media app

“Upload a photo, tag friends, add a caption, and share it.”

upload a photo
tag friends
add a caption
share it
scenario passed

Requirements-based testing turns each requirement into tests: the 5-second transfer rule becomes timed tests for normal, inter-bank and peak-time transfers.

Scenario testing acts out a realistic story from start to finish. Each step may pass alone, but the scenario checks they work together.

8.3.3 · Release testing

Performance testing

  • Definition: evaluates how the software performs under various conditions, such as load, stress and scalability.
  • Goal: identify bottlenecks, ensure stability, and guarantee the application performs well under real-world usage.

Example · online gaming appDevelopers simulate thousands of players joining a game at the same time to see if the server can handle the load. Try it: drag the slider.

Performance tests check emergent properties such as response time and reliability. A good approach is an operational profile, a set of tests that reflects the real mix of work the system will handle.

The simulator is illustrative: response time stays low up to the design limit of 60,000 players, then climbs as the server saturates. Past about 82,000 players requests start timing out. The load test checks the expected range; the stress test pushes past it on purpose.

8.4 · User testing

User testing

Users or customers provide input and advice on system testing, because their real working environment affects a system's reliability, performance, usability and robustness.

Alpha testing

Users work with the development team to test the software at the developer's site.

When: developing shrink-wrapped products; users get early news of features.

Early bug detection · lower cost

Beta testing

A release of the software is made available to users so they can experiment and raise problems they discover.

When: an early, sometimes unfinished release is ready for evaluation.

Real-world feedback · less rework

Acceptance testing

Customers test a system to decide whether or not it is acceptable. Acceptance implies that payment should be made for the system.

When: the customer formally decides whether to accept the system.

Validates requirements · agreement to pay

Alpha testing brings selected users into development early, at the developer's site. Beta testing hands an early release to a wider group who use it in their own environments. Acceptance testing is the formal step in custom development: the customer decides whether the system is good enough to accept and pay for.

8.5 · Conclusion

Testing turns hope into evidence

Software testing is essential for ensuring a product's quality, reliability and performance.

It helps identify and fix issues early, reducing post-release risks and costs.

Through various testing methods, we validate that software meets requirements and delivers a positive user experience.

Built into modern practices like Agile and DevOps, testing supports faster, higher-quality releases, so organisations can deliver dependable software that meets user needs.

✓ V&V✓ development✓ TDD✓ release✓ user5 passing · 0 failing

To sum up: testing gives us confidence, not proof, that software is fit for purpose. Development testing finds bugs early, TDD builds a regression suite as you go, release testing validates the whole system, and user testing brings in the real environment.

In Agile and DevOps teams these tests run automatically on every change, which is what makes frequent, safe releases possible.
