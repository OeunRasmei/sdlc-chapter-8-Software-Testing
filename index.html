8 · Introduction

Testing has two distinct goals

Software testing is an important process in the software development lifecycle. It checks the software from two directions.

Verification

“Are we building the product right?”

The software should conform to its specification: its functional and non-functional requirements.

vs
Validation

“Are we building the right product?”

The software should do what the customer really requires.

Barry Boehm summed these up in 1979. Verification: are we building the product right, meaning does it match the specification? Validation: are we building the right product, meaning does it do what the customer actually needs?

A system can pass verification and still fail validation if the specification itself was wrong.

8 · Verification and validation goals

The goal is confidence, not perfection

✓

Establish confidence that the software is fit for purpose.

✗

Not proof that it is completely free of defects. That is generally not an achievable goal.

✓

Good enough for its intended use. The type of use decides how much confidence is needed.

The confidence needed depends on
Software purposeUser expectationsMarketing environment
How much confidence is enough?
Mobile game prototypeLow

A crash costs the player a restart.

Online shop checkoutHigh

A bug costs sales and customer trust.

Aircraft flight controlCritical

A bug can cost lives, so testing is exhaustive and regulated.

V&V aims to establish confidence that the system is fit for purpose. Defect-free software is not a realistic target.

Sommerville lists three things that set the level of confidence: the software's purpose (how critical it is), user expectations (users tolerate some bugs in new or cheap software), and the marketing environment (getting to market early can matter more than finding every defect).

8 · Verification techniques

Inspections and testing work together

Inspection: static, the code is not runTesting: dynamic, the code is run
Why inspect as well as test?
  1. Errors can't hide other errors, so one inspection can find many defects at once.
  2. Incomplete versions can be inspected without building a test harness.
  3. Inspections also judge standards, portability and maintainability.

But inspections can't measure performance or usability. They complement testing; they don't replace it.

Verification uses two techniques. Software inspections analyse static artefacts such as the requirements, design models, database schemas and the source code itself. Testing runs the program, or a prototype, with test data.

Sommerville gives three advantages of inspections: one error can't mask another, incomplete versions can be inspected, and broader quality attributes can be checked. Testing is still needed for things that only show up at run time.

8 · An input-output model of testing

Two ways to use a test

Validation testing

Show the software meets its requirements, using test cases that reflect expected use. A successful test shows the system working as intended.

Defect testing

Find inputs that make the software misbehave. Tests are designed to expose defects, and a successful test is one that makes the system fail.

Iₑ: inputs causing anomalous behaviour · Oₑ: outputs that reveal defects

This is Sommerville's input-output model. Every possible input is in the top set; the system turns inputs into outputs.

Validation testing uses normal, expected inputs (the white dots) to show the system works. Defect testing deliberately goes looking for the subset Iₑ (red) that produces faulty outputs Oₑ. Use the buttons to show each flow on its own.

Section 8.1

Development
testing

Development testing is the responsibility of the software development team. It happens while the system is being built, and its main job is to find bugs.

Later, a separate team tests the system before it is released to customers. In user testing, customers or system users provide test data and check that tests are successful.

Unit testingOne function, method or object class, tested in isolation.
Component testingSeveral units combined, tested through one interface.
System testingAll components integrated and tested as a whole.
  1. Stage 1 · nowDevelopment testingDevelopment team
  2. Stage 2Release testingSeparate testing team
  3. Stage 3User testingCustomers and users

A commercial system goes through three stages of testing: development testing by the team building it, release testing by a separate team, and user testing by customers.

Inside development testing there are three levels, from small to large: unit, component and system testing. Development testing is mainly defect testing: the aim is to find bugs.

8.1.1 · Development testing

Unit testing

Unit testing is the process of testing individual components in isolation.

A unit can be a single function or method, or a whole object class with several attributes and methods.

Goal: complete test coverage of a class
  • Test all operations associated with the object
  • Set and interrogate all object attributes
  • Exercise the object in all possible states

Units are the smallest testable parts: functions and methods, or object classes.

Sommerville's example is the WeatherStation class from the wilderness weather system. Complete coverage means calling every operation, setting and reading the identifier attribute, and driving the object through its state model, for example Shutdown → Running → Shutdown, or Configuring → Running → Testing → Transmitting → Running.

8.1.1 · Unit testing

Automate it: setup, call, assert

Unit tests should be automated so they run every time the code changes. A framework such as JUnit, pytest or Jest runs them and reports pass or fail.

1 · Setup

Initialise the system with the test case: the inputs and the expected outputs.

2 · Call

Call the object or method being tested.

3 · Assert

Compare the result with the expected result. True means the test passed; false means it failed.

Mock objects stand in for slow or unfinished parts, such as a database, so the unit can be tested on its own.

test_weather_station.py
from weather import WeatherStationfrom mocks import FakeInstruments def test_shutdown_stops_instruments():    # setup    kit = FakeInstruments(["thermometer", "anemometer"])    station = WeatherStation("WS-042", kit)    # call    station.shutdown(kit.all())    # assertion    assert station.state == "Shutdown"    assert kit.running() == []
$ pytest -q
. 1 passed in 0.02s

Automated tests have three parts. Setup prepares the object and the expected result. Call runs the operation under test. Assertion compares the actual and expected results.

Here the instruments are a mock object, so the test doesn't need real weather hardware. Because the tests are automated, the whole suite can be re-run in seconds after every change.

8.1.2 · Development testing

Choosing unit test cases

Two types of unit test case

NORMALShow it works

Test cases that show the component behaves correctly under normal use, for example by demonstrating part of a use case.

login("dara", "c0rrect-pw") → "Welcome, Dara"

ABNORMALExpose the bugs

Test cases that expose defects. For example, invalid input should produce an error message and fail gracefully.

login("", "") → "Please enter your username"
Two strategies for choosing them

Partition testing

Identify groups of inputs that have common characteristics and should be processed in the same way. Choose tests from within each of these groups.

ages: [<0 invalid] [0–17 minor] [18–120 adult] [>120 invalid]

Guideline-based testing

Use testing guidelines based on the kinds of errors that programmers often make. Choose tests based on these guidelines.

empty list · one item · first/middle/last · overflow

Testing is expensive, so test cases must be chosen well. Every component needs both kinds: tests that show it works under normal use, and tests that probe for defects with abnormal inputs.

The two strategies are partition testing, which groups inputs into classes that behave the same way, and guideline-based testing, which uses experience of common programming mistakes. The next two slides show each one.

8.1.2 · Partition testing

Specification: the program accepts 4 to 10 inputs, and each input is a five-digit integer from 10000 to 99999.

Boundary values are where bugs cluster. Test just inside and just outside every boundary: 3, 4, 10, 11 and 9999, 10000, 99999, 100000. Ariane 5 failed at exactly this kind of boundary.

This is Sommerville's partition example. Inputs fall into equivalence partitions: groups the program should treat the same way. Pick one test from the middle of each partition and, above all, tests at the boundaries.

Drag the sliders or click the test values to show which partition a value falls in and what the program should do. Values like 9999 and 100000 sit just outside the valid range and should be rejected with an error.

8.1.2 · Guideline-based testing

Test where programmers usually slip

General guidelines (Whittaker, 2009)
  1. Choose inputs that force the system to generate every error message.
  2. Design inputs that cause input buffers to overflow.
  3. Repeat the same input or series of inputs many times.
  4. Force invalid outputs to be generated.
  5. Force computation results to be too large or too small.

CrowdStrike, 2024: an update with 21 fields where the code expected 20. Exactly the wrong-sized input guideline 2 targets.

Sequences, arrays and lists
  1. Test with sequences that have only a single value.
  2. Use sequences of different sizes in different tests.
  3. Access the first, middle and last elements.
  4. Test with sequences of zero length.
single value[7]
first · middle · last[38194]
zero length[empty]

Guidelines capture experience of where defects hide. James Whittaker's general guidelines force error messages, overflow buffers, repeat inputs, and push outputs and calculations out of range.

For anything that processes a sequence, test a single value, different lengths, the first, middle and last elements, and an empty sequence. Programmers often assume a list is never empty, and that assumption breaks code.

8.1.3 · Development testing

Component testing

Software components are made up of several interacting objects (or sub-components).

  • The functionality of these objects is accessed through the defined component interface.
  • Component testing demonstrates that the interface behaves according to its specification, assuming the sub-components (objects) have already been unit-tested.
Parameter

Data or function references are passed from one component to another.

Shared memory

A block of memory is shared between components.

Procedural

A component encapsulates a set of procedures that others call.

Message passing

Components request services by passing messages.

A component bundles several objects behind one interface. Tests are written against that interface, not the objects inside, on the assumption that each object already passed its unit tests.

There are four kinds of interface: parameter, shared memory, procedural and message passing. The kind of interface affects the errors you look for, which is the next slide.

8.1.3 · Interface testing

Three ways interfaces break

01

Interface misuse

A component calls another and uses its interface wrongly, for example with parameters in the wrong order.

02

Interface misunderstanding

The calling component makes wrong assumptions about how the called component behaves.

03

Timing errors

The components run at different speeds, so out-of-date information is accessed.

Interface testing guidelines
Extreme parameter valuesNull pointersTests that make it failStress message passingVary activation order
Case study · Mars Climate Orbiter, 1999 · misunderstanding
Ground software1.0 lbf·s
1.0
Navigation softwareread as 1.0 N·s

1 lbf·s = 4.45 N·s, so every thruster burn was under-counted. Over ten months the error pushed the probe low enough to burn up. A test across that interface would have caught it.

Interface errors are among the most common errors in complex systems. Sommerville groups them into misuse, misunderstanding and timing errors.

The Mars Climate Orbiter is a classic misunderstanding: one team's software produced impulse in pound-force seconds and the other team's software assumed newton seconds. Each module worked on its own; the failure lived in the interface.

Guidelines: test parameters at the extremes of their ranges, pass null pointers, design tests that cause the component to fail, stress-test message passing, and vary the order in which components using shared memory are activated.

8.1.4 · Development testing

System testing

Integrate components to create a version of the system, then test the integrated system.

It checks that components
  • are compatible
  • interact correctly
  • transfer the right data at the right time across their interfaces

It tests the interactions between components, including emergent behaviour that only appears when the parts run together.

Use-case-based testing: each use case involves several components. Its sequence diagram shows which interactions to test.

Use case: collect weather data (simplified from Sommerville's weather station example)

System testing integrates the components and tests the result. It overlaps with component testing, with two differences: reusable and off-the-shelf components are integrated with new ones, and components built by different people come together for the first time.

Use cases make good system tests because each one exercises several components. The sequence diagram for "collect weather data" tells you exactly which messages should flow and in what order. The animation plays them in sequence.

Section 8.2

Test-driven
development

Test-driven development (TDD) is an approach to program development in which testing and code development are interleaved (Beck, 2002; Jeffries and Melnik, 2007).

01 · WRITE A TESTRed

Write a small test for the next piece of behaviour. It fails, because the code doesn't exist yet.

02 · MAKE IT PASSGreen

Write just enough code to make the test pass, and keep every older test passing.

03 · IMPROVERefactor

Clean up the code without changing what it does. The tests stay green.

TDD came out of Extreme Programming. Kent Beck's 2002 book made it popular. Instead of writing code and testing it later, you write the test first.

The rhythm developers use is red, green, refactor: a failing test, the simplest code that passes, then a clean-up while the tests protect you.

8.2 · The TDD process (Figure 8.9)

Red, green, refactor, repeat

1/5Identify a small increment of functionality, normally a few lines of code.

2/5Write a test for it and implement the test as an automated test.

3/5Run it with all the other tests. It fails, because the code doesn't exist yet.

4/5Implement the functionality and refactor, then run the tests again.

5/5All tests pass. The new code is now protected by its own test.

nextMove on to the next chunk of functionality and repeat the cycle.

cart.test.js
// Feature: orders over $100 get 10% offtest("10% off orders over $100", () => {  expect(total(120)).toBe(108);}); function total(amount) {  return amount > 100 ? amount * 0.9 : amount;}

This is Figure 8.9. Identify a small piece of new functionality, write an automated test for it, and run it with all the other tests. It fails, so you implement the functionality and refactor, then run the tests again. When everything passes, move to the next piece.

The editor on the right plays a real cycle: the test for a 10% discount fails first because total() doesn't exist, then passes once it is written. The same discount comes back in the release testing example.

8.2 · Test-driven development

Four benefits of writing tests first

Code coverage

Every piece of code has at least one test, so high coverage means the code is thoroughly tested.

Regression testing

The test suite grows with the code. Re-running it checks that new changes or additions haven't broken anything.

let sum = 0;
for (const i of items)
sum += i.price * 0.9;
return round(sum);

Simplified debugging

When a test fails, the problem can usually be pinpointed to the code just written.

applies 10% off over $100
rejects negative totals
free shipping over $200
rounds to 2 decimals

System documentation

The tests describe what the code is supposed to do, and they never go out of date.

Sommerville notes TDD works best for new development. It helps less with large legacy systems and is harder to apply to multithreaded code.

Code coverage: every code segment has at least one associated test. Regression testing: a suite develops incrementally and can be run after every change, which is cheap because it's automated. Simplified debugging: a failing test points at the code you just wrote. Documentation: tests read as a description of what the code should do.

Studies of TDD are mixed on productivity, but most report better code quality and better understanding of the code.

≡

Release testing checks a particular release of a system that is intended for use outside the development team.

Sommerville stresses two differences from system testing: it should be done by a separate team that has not been involved in development, and its aim is validation, showing the system is good enough to use, rather than finding bugs. It is usually black-box testing based on the specification.

8.3.1 · Release testing

Requirements-based testing

  • Definition: a testing method focused on verifying that the software meets each specified requirement.
  • Process: test cases are designed to cover individual requirements, so each one is checked as correctly implemented.
  • Traceability: every requirement links to at least one test, so nothing is left untested.
Requirement · banking app

“Users must be able to transfer money in less than 5 seconds.”

TC-1Transfer $50 between own accounts1.8 s ✓

Requirements should be testable. For each requirement you derive a set of tests that show the requirement has been met. Here the banking requirement "transfer in less than 5 seconds" becomes several timed tests: a normal transfer, a transfer to another bank, one at peak load and an error case.

Sommerville's own example is from the Mentcare system: if a patient is allergic to a medication, prescribing it must issue a warning. The tests cover a patient with no allergies, one allergy, two allergies, and the prescriber overriding the warning.

8.3.2 · Release testing

Scenario testing

  • Definition: validates complex user workflows or end-to-end tasks, so the software behaves as expected in real-world use.
  • Purpose: makes sure users can complete typical or critical tasks without issues. It finds problems that individual functional tests miss.

8.3.3 · Release testing

Performance testing

  • Definition: evaluates how the software performs under various conditions, such as load, stress and scalability.
  • Goal: identify bottlenecks, ensure stability, and guarantee the application performs well under real-world usage.

Performance tests check emergent properties such as response time and reliability. Sommerville recommends building an operational profile, a set of tests that reflects the real mix of work the system will handle.

8.3.3 · Performance testing

Three types of performance testing

Load testing

Assesses performance under expected user loads.

Stress testing

Tests performance under extreme conditions, beyond the design limit, to see how the system fails.

Scalability testing

Ensures the system can grow to handle increased loads, for example by adding servers.

In software testing, “load” could mean
the number of users accessing the softwarethe volume of transactionsthe amount of data processed at a given time

Load testing uses the expected workload. Stress testing deliberately overloads the system past its maximum design load. Sommerville points out two reasons: it tests failure behaviour, since the system should fail-soft rather than collapse or corrupt data, and it reveals defects that only show up under full load.

Scalability testing checks the system can grow, for example by adding servers, and still meet its targets.

User
testing

What is user testing?

A stage in the testing process in which users or customers provide input and advice on system testing.

Why it's essential

Even after comprehensive system and release testing, influences from the user's working environment significantly affect a system's

reliabilityperformanceusabilityrobustness
  1. Stage 1 · doneDevelopment testingDevelopment team
  2. Stage 2 · doneRelease testingSeparate testing team
  3. Stage 3 · nowUser testingCustomers and users

Why involve users when we've already tested so much? Because developers can't replicate the user's real environment: their data, their workflow, their hardware, the interruptions in their day. Those factors change how reliable, fast, usable and robust the system really is.

8.4 · User testing

Three types of user testing

Alpha testing

Users work with the development team to test the software at the developer's site.

Where: developer's site

Beta testing

A release of the software is made available to users so they can experiment and raise problems they discover.

Where: users' own environment

Acceptance testing

Customers test a system to decide whether or not it is acceptable. Acceptance implies that payment should be made for the system.

Where: customer's site, under contract

Alpha testing brings selected users into development early, at the developer's site. Beta testing hands an early release to a wider group who use it in their own environments. Acceptance testing is the formal step in custom development: the customer decides whether the system is good enough to accept and pay for.

8.4 · User testing

When should we use each type?

START

Alpha testing

Used when developing shrink-wrapped software products. Users are willing to take part because it gives them early information about new system features.

staff try a new app build in-house

Beta testing

Used when an early, sometimes unfinished, release of a software system is made available to customers and users for evaluation.

Gmail was a public beta from 2004 to 2009

Acceptance testing

Used when a customer formally tests a system to decide whether or not it should be accepted from the developer.

a hospital signs off a records system before paying

Read it as a timeline. Alpha testing happens during development, mostly for packaged products. Beta testing comes with an early release to a wider audience; Gmail famously kept its beta label from its 2004 launch until 2009. Acceptance testing comes last, when a customer formally decides whether to accept the system from the developer.

Alpha testing catches problems early, when they are cheapest to fix, and prepares the product for beta. Beta testing adds real-world feedback at scale and finds issues nobody anticipated. Acceptance testing confirms the requirements are met, which supports a smooth deployment and the agreement to pay.

8.4 · Acceptance testing

Six stages of acceptance testing

Acceptance testing is part of custom systems development. It takes place after release testing, and the customer makes the final decision.

Define acceptance criteria→ test criteria
Plan acceptance testing→ test plan
Derive acceptance tests→ tests
Run acceptance tests→ test results
Negotiate test results→ testing report
Accept or reject system→ decision
In agile methods

There is no separate acceptance phase. The customer is part of the team, writes tests from user stories, and the tests run automatically with every change. The open question: is that one embedded user typical of everyone who will use the system?

Sommerville's acceptance testing process has six stages: define acceptance criteria (ideally in the contract), plan the testing, derive the tests, run them, negotiate the results (it's rare that every test passes), and finally accept or reject the system.

In practice, even with outstanding problems, a system is often accepted if it's usable, with the problems fixed later.

8.5 · Conclusion

Testing turns hope into evidence

Software testing is essential for ensuring a product's quality, reliability and performance.

It helps identify and fix issues early, reducing post-release risks and costs.

Through various testing methods, we validate that software meets requirements and delivers a positive user experience.

Built into modern practices like Agile and DevOps, testing supports faster, higher-quality releases, so organisations can deliver dependable software that meets user needs.

✓ V&V✓ development✓ TDD✓ release✓ user5 passing · 0 failing

To sum up: testing gives us confidence, not proof, that software is fit for purpose. Development testing finds bugs early, TDD builds a regression suite as you go, release testing validates the whole system, and user testing brings in the real environment.

In Agile and DevOps teams these tests run automatically on every change, which is what makes frequent, safe releases possible.
